How Payload publishing reaches ATF.org

Your original picture was right: Payload exposes content and the public site consumes it. The missing decision is when that consumption happens.

Publish changes data, not website files

Editor uses Payload Admin
→
Payload stores a published document
→
ATF.org requests that document

With Payload drafts enabled, documents have a status such as draft or published. Clicking Publish updates the document's published state in PostgreSQL. Proper access control allows unauthenticated visitors to read published documents while keeping drafts private.

Payload does not automatically rebuild or push pages into the Vite application. It makes the published document available. ATF.org decides when to ask for it.

The generated REST endpoint can look like GET https://cms.atf.org/api/news. The CMS origin is a configuration value, so local development can instead use http://localhost:3001/api/news. See Payload's REST API and Drafts documentation.

Four moments when ATF.org can read

Simplest live model

1. Browser runtime

A visitor opens ATF.org; the React app fetches Payload's public REST API. Published changes appear immediately without rebuilding the site.

Cost: news needs the CMS network request. The app must handle timeouts, CORS, and unavailable data gracefully.

Static snapshot

2. Build time

The site build fetches Payload and bakes the result into static files. Publishing commonly triggers a CI build through a Payload hook. That CI need not be Vercel.

Cost: content appears only after a successful rebuild, but the published site survives a CMS outage.

Needs a web server

3. Server runtime

A server fetches Payload for each request or through a shared cache, then returns rendered content to the visitor.

Cost: this adds a server runtime that the current static Vite application does not have.

More resilient, more logic

4. Hybrid

Ship a static snapshot, then ask Payload for fresher content in the browser. If the request fails, retain the snapshot.

Cost: two content paths must agree about schema, freshness, loading, and failures.

For ATF's current simplicity goal: browser-runtime REST is the natural first option to evaluate. It matches your mental model and works with any static host. The next question is whether a neutral “news unavailable” state is enough during a CMS outage. If stale news must remain visible, build-time or hybrid delivery earns its extra machinery.

Preview is a separate path

Public delivery should expose only published documents. Editorial preview deliberately reads draft data with authentication. Payload's Live Preview loads the frontend in an iframe inside the Admin Panel and sends edits to it using browser messages. A React frontend is supported, so the Vite site can gain preview behavior later without becoming part of the Payload application.

Primary source: Payload Live Preview.

One repository, two applications

ATF repository/
├── package.json          # Vite public site; bun run dev → :3000
└── backend-cms/
    └── package.json      # Payload app; npm run dev → :3001

Neither application needs Vercel or Nginx Proxy Manager to run. Those are deployment adapters. In production, the public site's CMS origin can be https://cms.atf.org; locally it can be http://localhost:3001.

Vercel supports selecting a project root in a repository, so the nested Payload app does not force a second repository or become part of the root site's build. See Vercel's monorepo documentation.
